# 10. Production-аудит реалізації

Дата аудиту: 2026-07-18.

Обсяг аудиту:

- колектори SMART і Sensors;
- JSON-контракти;
- updater-скрипти та спільні runtime-бібліотеки;
- systemd services і timers;
- `install.sh`, `upgrade.sh`, `uninstall.sh`;
- конфігурація Zabbix Agent 2;
- шаблони Zabbix;
- автоматичні тести та CI.

## Загальний висновок

Архітектура з попереднім збором даних у JSON-кеш є правильною для production: важкі команди не запускаються під час кожного опитування Zabbix. SMART collector має детерміновані fixture-тести та розширений JSON-контракт версії 2.

Водночас поточна реалізація ще має дефекти, які необхідно усунути перед остаточним production-релізом. Найкритичніші проблеми стосуються інсталятора, приховування помилок Sensors collector, відсутності timeout у systemd services та недостатньої перевірки шаблонів Zabbix.

## Критичні зауваження

### 1. Sensors collector приховує помилки виконання

Команда `sensors -j` виконується з `|| true`, а stderr повністю відкидається. У разі помилки колектор формує валідний JSON із порожнім масивом `readings`.

Наслідки:

- Zabbix не відрізняє відсутність сенсорів від аварії `sensors`;
- пошкоджений або неповний кеш виглядає успішним;
- немає полів `status`, `errors`, `duration_ms` та коду завершення команди;
- SMART і Sensors використовують різні службові контракти.

Необхідно перевести Sensors collector на JSON-контракт версії 2 зі статусами `ok`, `empty`, `degraded` і `error`.

### 2. Інсталятор не перевіряє production-платформу

`install.sh` не перевіряє:

- Debian 13;
- Proxmox VE 8;
- Zabbix Agent 2 7.4;
- наявність і працездатність `zabbix-agent2`;
- структуру початкових файлів проєкту перед внесенням змін.

Інсталяція може початися на непідтримуваній системі та завершитися частково.

### 3. Некоректна перевірка `--modules`

Поточна перевірка приймає будь-яке значення, якщо воно містить хоча б `smart` або `sensors`.

Наприклад, значення `smart,unknown` проходить перевірку, хоча містить непідтримуваний модуль.

Необхідний точний розбір списку з відхиленням:

- невідомих значень;
- порожніх елементів;
- дублікатів;
- пробілів;
- порожнього списку.

### 4. Конфігурація Zabbix Agent 2 не враховує вибрані модулі

Файл `zabbix/linux-monitoring.conf` завжди містить aliases для SMART і Sensors. Він встановлюється повністю навіть при `--modules smart`.

Наслідок: alias непідтримуваного на конкретному сервері модуля посилається на відсутній кеш і повертає unsupported item.

Інсталятор повинен генерувати конфігурацію лише для реально вибраних модулів.

### 5. Небезпечне створення тимчасового файла

Timer-файл створюється як `/tmp/linux-monitoring-${module}.timer.$$` через перенаправлення shell.

Для root-процесу це створює ризик атаки через symbolic link. Необхідно використовувати `mktemp`, встановити `umask 077` і гарантовано видаляти тимчасові файли через `trap`.

### 6. systemd services не мають timeout

SMART і Sensors services не містять `TimeoutStartSec=`.

Завислий `smartctl`, драйвер, HBA або `sensors` можуть залишити oneshot service активним без обмеження часу. Необхідно встановити обґрунтований timeout та перевірити його на реальному обладнанні.

## Важливі зауваження

### 7. Відсутні машинно-перевірні JSON-схеми

Наявність `schema_version` не замінює формальний контракт. CI перевіряє валідність JSON fixture-файлів і окремі значення, але не перевіряє:

- обов’язкові поля;
- типи полів;
- допустимі значення `status`;
- структуру елементів `disks` і `readings`;
- сумісність шаблонів Zabbix із версією схеми.

Необхідно додати schema-тести або еквівалентну сувору перевірку контрактів. Додавання окремих schema-файлів допустиме лише разом із повними тестами та реальним застосуванням у CI.

### 8. SMART підміняє відсутні метрики нулями

Функція нормалізації SMART повертає `0` для багатьох відсутніх полів.

Це змішує два різні стани:

- пристрій повідомив фактичне значення `0`;
- пристрій не підтримує або не повернув метрику.

Для production-моніторингу відсутня метрика повинна бути `null` або явно позначена як недоступна. Інакше Zabbix може показувати хибно нормальний стан.

### 9. Значення SMART support за замовчуванням оптимістичні

Поля `smart_available` і `smart_enabled` за відсутності відповідних даних отримують `true`.

Невідомий стан не повинен автоматично вважатися справним. Необхідно використовувати `null` або окремий статус невизначеності.

### 10. Runtime-параметр `LM_CACHE_DIR` не узгоджений із systemd sandbox

Updater дозволяє змінити `LM_CACHE_DIR`, але systemd service дозволяє запис лише в `/var/lib/linux-monitoring` через `ReadWritePaths=`.

Будь-яке інше значення призведе до помилки запису кешу. Потрібно або:

- зафіксувати каталог кешу як незмінний production-шлях;
- або генерувати коректний systemd override для вибраного каталогу.

Перший варіант є простішим і безпечнішим.

### 11. Інтервал timer не перевіряється

`--timer-interval` безпосередньо підставляється в unit-файл через `sed`.

Необхідно:

- перевіряти формат systemd time span;
- заборонити символи нового рядка;
- відхиляти нульові та надто короткі інтервали;
- мати production-мінімум, щоб не створити надмірне навантаження на диски.

### 12. Повторна інсталяція іншого набору модулів залишає старі компоненти

Якщо спочатку встановити `smart,sensors`, а потім виконати інсталяцію з `--modules smart`, старий Sensors timer і файли можуть залишитися активними.

Потрібно явно визначити семантику `--modules`: це повний бажаний стан, а не лише список компонентів для копіювання.

### 13. Немає транзакційного rollback

Інсталятор змінює пакети, конфігурацію, systemd units і Zabbix Agent 2 послідовно. При помилці в середині процесу автоматичне повернення попереднього стану відсутнє.

Необхідні:

- резервні копії змінюваних конфігурацій;
- попередня перевірка всіх вхідних файлів;
- `systemd-analyze verify` перед встановленням unit-файлів;
- `zabbix_agent2 -t` після встановлення aliases;
- зрозуміла інструкція ручного rollback.

## Аудит systemd

Позитивні властивості:

- `Type=oneshot`;
- запуск від `root` обмежений потребою доступу до обладнання;
- `NoNewPrivileges=true`;
- `PrivateTmp=true`;
- `ProtectHome=true`;
- `ProtectSystem=strict`;
- `ReadWritePaths=/var/lib/linux-monitoring`;
- знижені CPU/I/O пріоритети.

Необхідно додатково розглянути й протестувати:

- `TimeoutStartSec=`;
- `UMask=0022`;
- `ProtectClock=true`;
- `ProtectKernelLogs=true`;
- `ProtectKernelModules=true`;
- `ProtectKernelTunables=true`;
- `ProtectControlGroups=true`;
- `RestrictSUIDSGID=true`;
- `LockPersonality=true`;
- `RestrictRealtime=true`;
- `SystemCallArchitectures=native`.

Для SMART не можна без перевірки вмикати `PrivateDevices=true` або надто суворий `DevicePolicy=closed`, оскільки колектор повинен читати реальні block devices.

## Аудит timers

Поточні timers використовують:

- `OnBootSec=2m`;
- `OnUnitActiveSec=5m`;
- `AccuracySec=30s`;
- `Persistent=true`.

Схема придатна для production. Для великої кількості серверів варто додати невеликий `RandomizedDelaySec`, щоб після одночасного старту вузлів колектори не запускалися синхронно.

## Аудит шаблонів Zabbix

### Недостатня перевірка в CI

CI виконує лише `yaml.safe_load`. Це доводить, що файл синтаксично є YAML, але не доводить, що:

- шаблон імпортується у Zabbix 7.4;
- UUID унікальні;
- item keys унікальні;
- master items існують;
- dependent items посилаються на правильний master item;
- JSONPath відповідає поточному `schema_version`;
- value types сумісні з `null`, boolean і числовими значеннями;
- trigger expressions коректні;
- шаблон не створює unsupported items.

### Відсутність контролю шаблонів у structural test

`tests/structure-test.sh` не вимагає наявності шаблонів Zabbix. Каталог `zabbix/templates` може бути порожнім, а CI все одно успішно завершить YAML-перевірку, оскільки glob не поверне жодного файла.

### SMART schema version 2 не контролюється шаблоном

Під час переходу SMART collector на schema version 2 файли шаблонів Zabbix не змінювалися. Старі поля збережені, тому базові items можуть працювати, але нові службові поля `status`, `errors`, `duration_ms` та `discovery.failed_count` не контролюються шаблоном.

Шаблон повинен мати:

- item версії схеми;
- item статусу колектора;
- item віку кешу;
- item кількості помилок;
- trigger на застарілий кеш;
- trigger на `degraded` або `error`;
- trigger на невідповідну версію схеми.

## Аудит тестів

Позитивно:

- усі shell scripts перевіряються через `bash -n`;
- використовується ShellCheck;
- використовується shfmt;
- SMART має детерміновані fixture-тести;
- атомарний запис кешу перевіряється;
- невалідний JSON не замінює кеш.

Відсутні обов’язкові тести:

- fixture-тести Sensors collector;
- помилка виконання `sensors`;
- порожній набір сенсорів;
- нестандартна вкладеність JSON `lm-sensors`;
- точна перевірка `--modules`;
- `--dry-run` без змін файлової системи;
- повторна інсталяція;
- зміна набору модулів;
- помилка `apt-get`;
- помилка `systemctl`;
- rollback;
- `systemd-analyze verify`;
- перевірка aliases через `zabbix_agent2 -t`;
- реальний імпорт шаблонів у Zabbix 7.4;
- перевірка відповідності JSONPath fixture-файлам.

## Порядок виправлення

1. Виправити Sensors collector і додати fixture-тести.
2. Посилити preflight та розбір параметрів `install.sh`.
3. Усунути небезпечні тимчасові файли та реалізувати rollback.
4. Узгодити вибрані модулі з aliases, units і файлами.
5. Додати timeout та перевірені hardening-параметри systemd.
6. Зафіксувати JSON-контракти та перевіряти їх у CI.
7. Розширити шаблони Zabbix службовими items і triggers.
8. Додати перевірку реального імпорту шаблонів у Zabbix Agent/Server 7.4.
9. Виконати повторну перевірку на Debian 13 і Proxmox VE 8 на реальному обладнанні.

## Статус компонентів після аудиту

| Компонент | Статус |
|---|---|
| SMART collector | Потребує виправлення семантики невідомих значень |
| Sensors collector | Потребує обов’язкового доопрацювання обробки помилок |
| JSON-контракти | Потребують формальної перевірки |
| Runtime-бібліотеки | Базова реалізація придатна, потрібне узгодження cache path |
| systemd services | Потребують timeout і додаткового перевіреного hardening |
| systemd timers | Придатні, рекомендована десинхронізація запусків |
| Інсталятор | Потребує критичних виправлень перед production |
| Zabbix Agent aliases | Потребують генерації за вибраними модулями |
| Шаблони Zabbix | Потребують semantic/import тестів і службового моніторингу |
| CI | Не доводить повну production-готовність |

До усунення критичних зауважень поточний код не слід позначати як остаточно перевірений production-реліз.
